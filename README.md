# Release Desk

Maintain local release records and generate Markdown notes grouped as Added, Changed and Fixed. Requires Python 3.10+; only the standard library is used.

`python3 release_desk.py notes 1.1.0` renders the included second release. `python3 release_desk.py versions` lists sample versions in numeric order. `samples/next-changes.json` is a candidate change list; to try registration without changing the sample store, use `python3 release_desk.py --store .state/releases.json add 1.2.0 samples/next-changes.json` and query that same store.

Version identifiers have exactly three nonnegative numeric components, without prefixes, prerelease suffixes or leading zeros. Each release has at least one single-line change with a recognized category. Existing versions cannot be replaced. Category order is fixed and the input order within a category is retained. This version does not inspect Git or publish packages.

`python3 release_desk.py diff 1.0.0 1.1.0` compares two registered versions in the same store and prints a single-line JSON object with `baseVersion`, `targetVersion` and the `added`, `removed` and `unchanged` entries of the target relative to the base. Entries match on category plus trimmed, case-sensitive text; duplicates pair up by occurrence. Comparing a version with itself or a higher with a lower version is allowed. The comparison is read-only and never infers actual product changes.

`ReleaseDesk.diff_config(base_version, target_version, base_config, target_config)` is a read-only structural comparison of two externally supplied JSON configuration objects, and `python3 release_desk.py diff-config 1.0.0 1.1.0 base.json target.json` reads both configurations from UTF-8 JSON files using the same `--store` selection. Both versions must already be registered (the whole store is validated first); comparing a version with itself or a higher with a lower version is allowed. The configurations come solely from the arguments or files — they are never written to the store and never inferred from change entries — and neither the passed objects, the files nor the store are modified, and no directory is created.

Each root configuration must be a JSON object. When the same field exists in both and both values are objects, comparison descends recursively; otherwise the complete values are compared. Arrays are never split: they compare as whole values and element order is significant, with objects inside arrays following the same object rules. A field or whole subobject present only in the target yields one `added` entry, one present only in the base yields one `removed` entry, both carrying `path` and `value`; a field present on both sides with differing values yields a `changed` entry carrying `path`, `before` (the base value) and `after` (the target value). All three arrays are always present, and identical configurations return three empty arrays. `path` is a JSON Pointer rooted at the empty string (`/a/b`, `/` for an empty field name), with `~` and `/` in field names escaped as `~0` and `~1`. Each array is sorted by path in Unicode code point order; key matching is case-sensitive with no Unicode normalization and empty key names are allowed. Booleans differ from numbers even when comparing `true` with `1`, numerically equal integers and floats compare equal, `null` differs from a missing field, and object key order is ignored.

An invalid or unknown version, invalid store content, a non-object root, a non-string key, a non-JSON value (including non-finite numbers) or a circular reference raises `ValueError`, while unreadable files raise `OSError`; the CLI additionally rejects encoding errors, JSON syntax errors and repeated object keys at any level (the same whole-file duplicate-key rule as everywhere), printing a single-line `error` object with exit 2 for any of these and the single-line result with exit 0 on success. A missing store is treated as empty and then reports both versions as unknown.

`ReleaseDesk.preview_config(base_version, target_version, base_config, target_config, current_config)` is a read-only three-way preview that checks whether applying the base→target plan would overwrite independent edits already present in the current configuration, and `python3 release_desk.py preview-config 1.0.0 2.0.0 base.json target.json current.json` reads all three configurations from UTF-8 JSON files using the same `--store` selection. Both versions must already be registered (the whole store is validated first); same-version and reverse-order pairs are allowed, just like `diff-config`. The configurations come solely from the arguments or files and follow the same validation, equality, pointer and key rules as `diff_config`, and nothing — the passed objects, the files, the store — is modified and no directory is created.

For each field, the plan is the base→target change. A field the plan does not change keeps its current presence state and value, including independent current edits and current-only fields. When the plan does change a field, a current value equal to the target is kept, a current state equal to the base adopts the target (whole additions and deletions included), and any other state is resolved field by field only when the field exists on all three sides and all three values are objects; otherwise it is one conflict at that path whose preview keeps the current field's presence state and value. Whole subobject additions and deletions, arrays (never split) and type changes are always judged as a whole, so a whole-value conflict never lists subpaths; every other non-conflicting change still enters the preview. Equality uses the `diff_config` rules, including `null` differing from a missing field and two missing fields being equal. The result holds only `baseVersion`, `targetVersion`, `canApply`, `config` and `conflicts`: `config` is the complete previewed object, `canApply` is true only when `conflicts` is empty, and each conflict holds only `path` plus `base`, `target` and `current`, each of those holding a `present` boolean and a `value` only when present. `path` uses the same JSON Pointer escaping as `diff-config`, and `conflicts` is sorted by path in Unicode code point order. For example, a target that changes the port while the current config only changes a timeout keeps both changes, while both sides changing the same port to different values keeps the current port and reports a `/port` conflict.

An invalid or unknown version, invalid store or a configuration violating the existing config validation rules raises `ValueError`, while unreadable files raise `OSError`; the CLI additionally rejects encoding errors, JSON syntax errors and repeated object keys at any level in any of the three files, printing a single-line `error` object with exit 2. A valid preview prints the single-line result with exit 0 even when it reports conflicts, and a missing store is treated as empty and then reports both versions as unknown. Neither success nor failure modifies the arguments, the input files or the store, or creates any file or directory.

`ReleaseDesk.resolve_config(base_version, target_version, base_config, target_config, current_config, decisions)` is a read-only confirmation layer over `preview_config`, and `python3 release_desk.py resolve-config 1.0.0 2.0.0 base.json target.json current.json decisions.json` reads the three configurations and the decisions from four UTF-8 JSON files using the same `--store` selection. Both versions must already be registered (the whole store is validated first); same-version and reverse-order pairs are allowed, and the configurations come solely from the arguments or files under the same validation, equality, pointer and key rules as `preview_config`. `decisions` is a JSON object, possibly empty, mapping original `preview_config` conflict paths to either the string `"target"`, the string `"current"` or a custom decision object; strings and custom objects may be mixed freely in the same map. Keys match verbatim using the same JSON Pointer escaping (`~0`, `~1`), with no trimming or Unicode normalization; only whole conflict paths are accepted — arrays, type changes and whole-object conflicts cannot be decided at subpaths, and non-conflict fields are rejected — and partial selections are allowed. Choosing `"target"` adopts that conflict's complete target-side presence state and value; choosing `"current"` keeps the current side and records the conflict as handled. When the chosen side is missing the field is deleted, and a `null` side value is kept as a value rather than treated as missing. Every other non-conflicting change and every independent current edit keeps its preview result.

A custom decision object holds a strict boolean `present`. When `present` is true the object holds exactly `present` and a required `value`; when `present` is false it holds exactly `present` and the field is deleted. `value` accepts any legal JSON value, including `null`, arrays and objects. The custom value replaces the selected field wholesale: objects, arrays and type changes are never recursively merged, and a value numerically or structurally equal to the target or current side still counts as a custom, handled decision. Every other non-conflicting change and every independent current edit keeps its preview result. For example, when the port is 80 on the base side, 8080 on the target side and 9000 on the current side, a `{"present": true, "value": 9001}` decision on `/port` confirms 9001 while an independently modified timeout keeps its current value.

The result holds only `baseVersion`, `targetVersion`, `canApply`, `config`, `conflicts` and `resolved`: `config` is the complete configuration after the choices, `conflicts` holds only the unchosen conflicts with their original details and current values, and `canApply` is true only when `conflicts` is empty. Each `resolved` entry holds only `path` and `choice`: `choice` is the confirmed string for side selections or `"custom"` for every custom selection. Both `conflicts` and `resolved` are sorted by path in Unicode code point order and are always present, even when empty. An invalid or unknown version, invalid store, a configuration violating the existing rules, a non-object decisions value, a non-string key, a key that is not an original conflict path, a choice that is neither a string nor an object, an illegal string choice, or a custom object with a missing field, an extra field, a non-boolean `present`, or a `value` containing a non-string key, a non-finite number, a non-JSON value or a circular reference raises `ValueError`, while unreadable files raise `OSError`; the CLI additionally rejects non-UTF-8 files, JSON syntax errors and repeated object keys at any level in any of the four files, printing a single-line `error` object with exit 2. A valid run prints the single-line result with exit 0 even when conflicts remain. Neither success nor failure modifies the arguments, the input files or the store, or creates any file or directory, and mutating nested values in the returned result never reaches the passed inputs.

`ReleaseDesk.apply_config(base_version, target_version, base_config, target_config, expected_config, decisions, current_path)` applies a confirmed plan to a local configuration file, and `python3 release_desk.py apply-config 1.0.0 2.0.0 base.json target.json expected.json decisions.json current.json` reads the base, target and expected configurations plus the decisions from four UTF-8 JSON files using the same `--store` selection and treats the fifth path as the write target. Both versions must already be registered (the whole store is validated first); same-version and reverse-order pairs are allowed, and a missing store is treated as empty and then reports both versions as unknown. The target file must already exist and must not be a symbolic link, and it must not be the same file as the store or as any of the four input files — textual path aliases and hard links are recognized — with violations raising `ValueError`; a missing target or any read or write failure raises `OSError`, and neither a missing target nor missing directories are ever created. The file is read as UTF-8 JSON under the same whole-file duplicate-key rule as everywhere (encoding, syntax and repeated-key errors raise `ValueError`), validated like any configuration, and compared with the expected snapshot using the existing configuration equality rules; any mismatch raises `ValueError` before anything is written. The change is then processed exactly like `resolve_config`: independent current edits are kept, side selections and custom decisions are accepted, decision keys must be original conflict paths (an empty decisions object is valid when there are no conflicts), and any conflict left undecided raises `ValueError`. The result holds only `baseVersion`, `targetVersion`, `changed`, `config` and `resolved`, where `config` and `resolved` carry the same content and path ordering as the `resolve_config` result and `changed` is true only when the final configuration differs semantically from the read one. When `changed` is true the target is replaced wholesale with UTF-8 JSON ending in a newline; when it is false the target's bytes and modification time are left untouched. Validation and read or write failures always preserve the target's original bytes, and neither success nor failure modifies the passed objects, the four input files or the store.

The API is `ReleaseDesk.add`, `versions`, `notes`, `diff`, `diff_config`, `preview_config`, `resolve_config`, `apply_config`, `import_releases`, `preview_import_releases`, `export_releases`, `checklist`, `check_dependencies`, `generate_checklist`, `audit_checklist`, `release_record`, `reconcile_checklist`, `migrate_checklist`, `update_checklist`, `preview_update_checklist`, `preview_merge_checklist` and `resolve_merge_checklist`. JSON is used for command results and errors except `notes`, which prints Markdown. Invalid input or file errors exit 2. Run `python3 -B -m unittest -v` for rendering, sorting, validation, diff, config diff, config preview, config resolution, config apply, import, preview, export, checklist, dependency checks, template filtering, audit, merge preview, merge resolution and CLI tests.

Every JSON file read from disk — the store, the `add` changes file and the `import` batch file — is rejected as a whole when any single object repeats a key, failing with `duplicate JSON object key` before anything is registered or written. Keys are compared exactly as decoded: case-sensitively, without trimming or Unicode normalization, so a key spelled with `\u` escapes still collides with its plain spelling. Identical change entries in an array remain legal.

`python3 release_desk.py import batches.json` merges multiple releases from a local JSON file that maps versions to change arrays, using the same validation as `add` and the `--store` target. It prints a single-line JSON object with numerically sorted `imported` and `skipped` arrays: an existing version is skipped only when its normalized categories, texts and order match exactly, and any count, order, category or text difference is a conflict that aborts the whole import. An empty object is valid and changes nothing; a missing target store is treated as empty and is not created when every release is skipped. Validation, conflicts and file errors leave any existing store byte-for-byte untouched. The import never reads Git or publishes packages.

`python3 release_desk.py import --dry-run batches.json` previews the same batch without writing anything. It prints a single-line JSON object with numerically sorted `imported` and `skipped` arrays, a `conflicts` array sorted the same way, and `canImport`, which is true only when no version conflicts. Each conflict detail carries `version` plus the `added`, `removed` and `unchanged` entries of the batch relative to the stored release, classified exactly like `diff` (fixed category order, trimmed case-sensitive texts, duplicates paired by occurrence, entries holding only `category` and `text`), and `orderOnly`, which is true only when the stored and batch arrays differ solely in entry order. Conflicts still exit 0 in preview mode, while an invalid batch, store or unreadable file fails with an `error` object and exit 2. The preview validates the whole store even for an empty batch, treats a missing store as empty, and never creates or modifies the store, its parent directories, the batch file or the passed payload. `ReleaseDesk.preview_import_releases(payload)` offers the same preview directly, raising `ValueError` on invalid batch or store content and `OSError` on read failures.

`python3 release_desk.py export` prints a single-line JSON object mapping versions to change arrays, exactly in the shape accepted by `import`: versions are sorted by numeric components and each entry contains only `category` and trimmed `text`, preserving the original array order, repeated entries and Chinese text as-is. Exporting without `--version` includes every release; repeated `--version` filters may be passed and duplicates are only kept once. A missing store is treated as an empty object and is never created, while selecting a version from an empty store fails as an unknown release. The whole store is validated regardless of selection, and exporting never modifies it; importing an export into an empty store imports every release, and importing it again skips every release.

With `--output file.json` the object is written as UTF-8 JSON ending in a newline, creating missing parent directories and replacing any existing file wholesale, and the command instead prints a single-line object whose `exported` value is the numerically sorted array of exported versions. Validation or write failures leave an existing target byte-for-byte untouched and never create a missing target. The output must not point at the store file, including textual path aliases, symlinks and hard links; doing so fails like any other invalid input.

`ReleaseDesk.checklist(version, payload)` is a read-only release readiness check, and `python3 release_desk.py check 1.2.0 checklist.json` runs it against a UTF-8 JSON file using the same `--store` selection. The checklist object holds `version` and `items`: the version follows the existing version rules and must equal the queried version, and `items` is a non-empty array containing at least one required check. Each item has `id`, `text`, `required` and `status` only; `id` and `text` are strings that are non-empty after trimming surrounding whitespace and are rejected when the raw value contains a carriage return or newline, `required` is a strict boolean, and `status` is one of `done`, `pending` or `blocked`. Normalized ids must be unique case-sensitively after trimming, with no Unicode normalization (`café` with U+00E9 differs from `caf` + `e` + U+0301), while duplicate item texts are legal. Extra object fields are ignored.

The command prints the same single-line report as the API, holding only `version`, `ready`, `done`, `pending` and `blocked`. The last three arrays group items by declared status, preserving the input order within each group, and each entry holds only the trimmed `id` and `text` plus the original `required` and `status`. `ready` is true only when every required item is `done`; unfinished or blocked optional items stay in their groups but never affect readiness. Status comes solely from the checklist — nothing is inferred from change texts. An invalid version, checklist structure or field, duplicate id, version mismatch, unknown release or invalid store content raises `ValueError`, and read failures raise `OSError`; the CLI reports these, plus non-UTF-8 or malformed JSON checklist files, as a single-line `error` object with exit 2, while a valid checklist prints its report with exit 0 regardless of readiness. The checklist file follows the same duplicate-JSON-key whole-file rejection rule. The whole store is validated, a missing store is treated as empty and then reports the version as unknown, and neither success nor failure modifies the store, the checklist file or the passed payload, or creates any file or directory.

`ReleaseDesk.check_dependencies(version, checklist, dependencies)` is a read-only dependency-aware variant of `checklist`, and `python3 release_desk.py check-dependencies 1.2.0 checklist.json dependencies.json` reads the checklist and a dependency map from two UTF-8 JSON files in that order using the same `--store` selection. The version, checklist and complete store checks follow `checklist` exactly — the declared checklist version must equal the queried version, the whole store is validated first, and a missing store is treated as empty and then reports the version as unknown. The dependency value is a JSON object, possibly empty, that maps an item id to the array of its direct prerequisite ids; an empty array and an omitted item both mean "no prerequisites". Every id on either end follows the checklist single-line id rule: a string non-empty after trimming surrounding whitespace, rejected when the raw value contains a carriage return or newline, matched case-sensitively after trimming with no Unicode normalization. Every array value must be an array, prerequisite ids must be unique within one array after normalization, normalized object keys must be unique, both ends must reference checklist items, and a self dependency or any cycle — even a cycle involving only optional items — is rejected. The dependency file follows the same duplicate-JSON-key whole-file rejection rule as every other file.

The report holds only `version`, `ready` and `items`. `items` keeps the checklist order, and each item carries the normalized `id`, `text`, `required` and the original declared `status`, plus `effectiveStatus` and `waiting`. `effectiveStatus` is `"blocked"` when any direct prerequisite is not effectively `done`, no matter what the item declared; otherwise it equals the declared status. Blocking propagates layer by layer: when A depends on B and B depends on C, with A and B declared `done` and C `pending`, both A and B are effectively blocked, while A's `waiting` lists only B. `waiting` is always an array and lists, in dependency-array order, only the direct prerequisites whose effective status is not `done`; transitive prerequisites are never listed. `ready` is true only when every required item is effectively `done`; optional items never decide readiness themselves, but an optional prerequisite that is not effectively done still blocks a required item that depends on it. With no dependencies the report's readiness is identical to `check`. An invalid or unknown version, a version mismatch, an invalid checklist or store, a non-object dependency value, an illegal id, a normalized duplicate key or duplicate array id, a non-array dependency value, a reference to an unknown item at either end, a self dependency or a cycle raises `ValueError`, and read failures raise `OSError`; the CLI additionally rejects non-UTF-8 files, JSON syntax errors and repeated object keys at any level in either file, printing only a single-line `error` object with exit 2. A valid run prints the single-line report with exit 0 even when it is not ready. Neither success nor failure modifies the passed objects, the input files or the store, or creates any file or directory, and mutating the returned data never reaches the inputs. All other public entry points keep their existing behavior.

`ReleaseDesk.generate_checklist(version, payload)` builds a pending checklist from a template, filtered by the change categories of a registered release, and `python3 release_desk.py make-checklist 1.2.0 template.json` reads the template from a UTF-8 JSON file using the same `--store` selection. The template object holds `items`, a non-empty array; each item has `id`, `text` and a strict boolean `required`, plus an optional `categories` array naming one or more distinct categories among Added, Changed and Fixed. Ids and texts follow the checklist rules (trimmed, non-empty, no carriage returns or newlines in the raw value) and normalized ids must be unique case-sensitively without Unicode normalization; every template item is validated, including ones the filter would drop. Items without `categories` always apply, and an item with `categories` is kept once when the release contains at least one of those categories — duplicate or same-category changes never repeat it. The result holds only `version` and `items`, in template order, each item carrying only the trimmed `id` and `text`, the original `required` and a uniform `pending` status; all other template fields, including any declared `status`, are ignored, so the output can be passed straight to `checklist` or `check`. For example, a release with only Fixed changes keeps generic items and Fixed items but drops Added-only ones. An invalid version, unknown release, invalid template or store content, an empty filtered result or a result without any required item raises `ValueError`, and read failures raise `OSError`; the CLI reports these, plus non-UTF-8 or malformed JSON template files and duplicate JSON object keys, as a single-line `error` object with exit 2. The whole store is validated, a missing store is treated as empty and then reports the version as unknown, and neither success nor failure modifies the store, the template file or the passed payload, or creates any file or directory.

`ReleaseDesk.audit_checklist(version, checklist, template)` is a read-only cross-check of a declared checklist against the template items applicable to the same release, and `python3 release_desk.py audit-checklist 1.2.0 checklist.json template.json` runs it on two UTF-8 JSON files using the same `--store` selection. Both inputs follow the existing checklist and template rules: the checklist version must equal the queried version, the template is filtered by the release's change categories exactly like `generate_checklist`, items the filter drops are still fully validated, and status is never inferred from change texts. Items are matched by their trimmed ids, case-sensitively and without Unicode normalization. The report holds only `version`, `ready`, `done`, `pending`, `blocked`, `missing`, `mismatched` and `unexpected`. The three status arrays are the same groups `checklist` would return, keeping every item and the input order within each group. `missing` lists applicable template items whose id has no checklist counterpart, each holding only `id`, `text`, `required` and a uniform `pending` status. `mismatched` lists same-id pairs whose normalized `text` or `required` differ, each entry holding only `expected` (the template-generated item) and `actual` (the checklist item), both normalized to the same four fields. `unexpected` lists checklist items whose id no applicable template item declares, again with only those four fields. `missing` and `mismatched` follow template order, `unexpected` follows checklist order. `ready` is true only when the checklist satisfies the existing readiness rule and every applicable required template item has a counterpart whose `id`, `text` and `required` match and whose status is `done`; differences in optional template items never affect readiness. An invalid version, unknown release, version mismatch, invalid checklist, template or store content, an empty filtered selection or a selection without any required item raises `ValueError`, and read failures raise `OSError`; the CLI reports these, plus non-UTF-8 or malformed JSON files and duplicate JSON object keys (whole-file rejection, as everywhere), as a single-line `error` object with exit 2, while a valid audit prints its report with exit 0 regardless of readiness. A missing store is treated as empty and then reports the version as unknown, and neither success nor failure modifies the store, the input files or the passed payloads, or creates any file or directory.

`ReleaseDesk.release_record(version, checklist, template, rollback)` freezes a release's changes, audit report and rollback plan into one read-only snapshot, and `python3 release_desk.py record-release 1.2.0 checklist.json template.json rollback.json` builds it from three UTF-8 JSON files using the same `--store` selection. The checklist and template follow the existing rules and the audit runs exactly like `audit_checklist`, including the category filter, id matching and the rule that optional template items never block readiness; when the resulting report is not `ready`, `ValueError` is raised and no new optional-item blocking is introduced. The rollback value must be an object holding exactly `targetVersion` and `steps`. `targetVersion` is either null or a registered version numerically smaller than the release version; an invalid, unknown or not-smaller value raises `ValueError`. `steps` is a non-empty array of single-line strings, each non-empty after trimming surrounding whitespace and rejected when the raw value contains a carriage return or newline; trimmed steps keep their array order and any duplicates.

The result holds only `version`, `changes`, `notes`, `audit` and `rollback`. `version` is the release version, `changes` is the exported change array with the same semantics as `export` (trimmed text, original order and duplicates preserved), `notes` is the existing Markdown summary text from `notes`, `audit` is the complete existing `audit_checklist` report, and `rollback` holds only `targetVersion` and the normalized `steps`. Identical inputs yield identical records with no generated timestamp, and mutating nested data in the returned record never reaches the passed inputs. Nothing is written to the store, the checklist, the template or the rollback file.

The command prints the single-line record JSON with exit 0 on success. With `--output file.json` the same record is additionally saved as UTF-8 JSON ending in a newline, without changing the console output; missing parent directories and read or write failures raise `OSError`, and the output path must not already exist — an existing file, a symbolic link (including a dangling one), or a textual alias or hard link pointing at the store or any of the three input files raises `ValueError`, so the snapshot is only ever written to a brand-new path. An invalid or unknown version, an invalid store, checklist or template, a malformed rollback plan, a non-UTF-8 file, a JSON syntax error or a repeated object key at any level raises `ValueError`; a missing store is treated as empty and then reports the version as unknown. On failure the command prints only a single-line `error` object with exit 2, preserves the original bytes of every existing file, and never leaves a new file or directory behind.

`ReleaseDesk.reconcile_checklist(version, checklist, template)` updates a same-version checklist against a revised template, keeping progress that is still valid and listing the items that need re-confirmation, and `python3 release_desk.py reconcile-checklist 1.2.0 checklist.json template.json` runs it on two UTF-8 JSON files using the same `--store` selection. Both inputs follow the existing checklist and template rules, including the checklist version match and the at-least-one-required-item rule: the checklist must stay valid on its own even when, for example, every old item has become inapplicable. The template is filtered by the release's change categories exactly like `generate_checklist` — including the empty-selection and no-required-item errors — and items the filter would drop are still fully validated, as is the whole checklist and the whole store. Ids match case-sensitively after trimming surrounding whitespace, without Unicode normalization. When the normalized `text` and `required` of a same-id pair are both identical, the old status is kept even if the template moved the item, and the id is listed in `retained`; when either differs, the item takes the new definition with a uniform `pending` status and the id is listed in `reset`; applicable template items absent from the old checklist are added with `pending` status and their ids go in `added`; old items no longer applicable — whether filtered out by category or missing from the new template — are dropped and their ids follow the old checklist order into `removed`. The result holds only `version`, `items`, `retained`, `reset`, `added` and `removed`; `items` follows the applicable template order, each entry carrying only the normalized `id`, `text`, `required` and `status`, and the three change arrays follow template order while `removed` follows the old checklist order; every array is present even when empty. The output needs no required item to be `done` and can be passed straight to `checklist`/`check` or `audit_checklist`; template-declared status is ignored and status is never inferred from changed wording. An invalid version, unknown release, version mismatch, invalid checklist, template or store content, an empty filtered selection or a selection without any required item raises `ValueError`, and read failures raise `OSError`; the CLI reports these, plus non-UTF-8 or malformed JSON files and duplicate JSON object keys (whole-file rejection, as everywhere), as a single-line `error` object with exit 2, while success prints the single-line result with exit 0. A missing store is treated as empty and then reports the version as unknown, and no result ever modifies the store, the input files or the passed payloads, or creates any file or directory.

`ReleaseDesk.migrate_checklist(base_version, target_version, checklist, template)` is a read-only cross-version migration that lets a target-version checklist inherit only check progress still backed by evidence in the target release, and `python3 release_desk.py migrate-checklist 1.0.0 2.0.0 checklist.json template.json` reads the base checklist and target template from two UTF-8 JSON files using the same `--store` selection. Both versions must already be registered (the whole store is validated first, then both versions are looked up); migrating a version to itself or migrating in reverse version order is allowed. The checklist follows the existing checklist rules and its declared version must equal the base version, while the template follows the existing template rules; the template is filtered by the **target** version's change categories exactly like `generate_checklist` — including the empty-selection and no-required-item errors — and template items the filter would drop are still fully validated, as is the whole checklist and the whole store.

Item ids match case-sensitively after trimming surrounding whitespace, without Unicode normalization. A target template item without a same-id old item is added with uniform `pending` status; a same-id item whose normalized `text` or `required` differs is redefined and reset to `pending`. When the definition is identical, the two releases are compared with the same category classification, trimmed-text matching, order-insensitive pairing and duplicate-count rules as `diff` — a change in the order of entries alone never resets an item — scoped to the categories the **new template item** declares: an item declaring no `categories` compares all three categories, and a multi-category item compares every category it declares, categories absent from the target release included. Only when every compared category is completely unchanged (nothing added and nothing removed in that category) between the two releases is the old status kept and the id listed in `retained`; otherwise the item takes the new definition with `pending` status and the id is listed in `reset`. For example, when only the Added entries change a Fixed-scoped done item stays `done`, while losing one of two duplicate Fixed entries resets even the Fixed item. Old items that do not appear in the filtered target selection — whether filtered out because the target release no longer has any of their declared categories or missing from the new template — are removed, their ids following the old checklist order.
